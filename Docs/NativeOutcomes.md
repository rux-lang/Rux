# Native Sums, Optionals, and Errors

This page records why the native outcome forms are shaped the way they are, why errors are values rather than unwound, where the compiler implements them, and how code written against the retired forms migrates. The user-facing rules themselves are in the language guide, under [Native Sums and Optionals](Language.md#native-sums-and-optionals) and [Errors](Language.md#errors-t--e-throw-and-the-error-forms); this page is the rationale and the map behind them. Revisit a decision here before changing the behavior that depends on it.

## Forms and Terms

| Form                    | Purpose                                                                                                 | Inspection                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `variant Event { ... }` | Alternatives distinguished by meaningful case names, even with identical payload types.                 | Named case patterns.                                           |
| `A \| B`                | One value of a set of distinct resolved types: a _sum_.                                                 | Typed patterns, qualified case patterns, `is`.                 |
| `T?`                    | A present `T` or absence: an _optional_, preserving every level.                                        | `p?`, `none`, typed presence patterns, `is`, `?`, `??`.  |
| `T ! E`                 | A success `T` or an error `E`: a _fallible_, what a function that can fail returns. `!E` has no value. | `x!`, `x !! v`, `x !!;`, `x catch { arms }`, typed patterns, `is`. |
| `()`                    | The built-in empty tuple, the _unit_, whose only value is also `()`.                                    | The pattern `()` or a binding.                                 |
| `union Storage { ... }` | Untagged overlapping storage.                                                                           | Field access.                                                  |

Diagnostics, lint messages, and these docs use one vocabulary: a _member_ is one type of a sum; a _level_ is one optional nesting step; presence is written as a value converted to the optional or the pattern `p?`, with `none` for absence; the _typed presence pattern_ is `v: T` on an optional subject. On the error side, a function's _error side_ is the type after `!` in its return type; a _throw site_ is the operand of a postfix error form, or a `throw`; and a _handler_ is a `catch`, `!!` or `!!;`, which receives the error of its own operand.

## Design Decisions

| #   | Topic                     | Decision                                                                                                                                                                                                                         | Reason                                                                                                           |
| --- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| D1  | Terminology               | `A \| B` is a _sum type_; `union` keeps naming overlapping storage.                                                                                                                                                              | Distinct storage contracts stay distinct in docs and diagnostics.                                                |
| D2  | Optional model            | `T?` is compiler-owned and non-collapsing; `T??` is distinct. There is no `None` type.                                                                                                                                           | Iterators and maps must tell a missing element from a present absent value.                                      |
| D3  | Optional construction     | `none` is outer absence; a value converts to presence, and an optional has no case to write.                                                                                                                                                             | Every nested state is constructible without temporaries.                                                         |
| D4  | Generic sums              | `T \| U`, `E \| Timeout`, and repeated outer constructors are legal; sums normalize after substitution and dependent operations are rechecked.                                                                                   | Sum identity is a set of types, not left/right provenance; instantiation-time diagnostics are the accepted cost. |
| D5  | Member order              | Canonical order derives from the stable fully qualified resolved identity.                                                                                                                                                       | Independently compiled objects agree on the same concrete type.                                                  |
| D6  | Unit success              | The unit is the empty tuple `()`; a function declaring `-> !E` completes with it.                                                                                                                                               | One error model, with no library type recognized by name.                                                        |
| D7  | Errors are values         | `T ! E` is a real type: returned, stored, passed and used in generics. A success converts to it; an error enters it only through `throw`, and a fallible converts to another only by identity or by widening its error sum.     | One type replaces both a separate error channel and a library `Result`, and keeping an outcome names no extra type. |
| D8  | Nesting                   | Nested optionals and optional error payloads are preserved; an optional error is grouped, `T ! (E?)`, and a fallible success is grouped, `(T ! E) ! F`.                                                                       | Composition never erases a level or turns an inner absence into an outer one.                                    |
| D9  | Conversion                | Identity first; otherwise exactly one permitted construction or widening route, and competing interpretations are rejected.                                                                                                      | Expected-type convenience never silently chooses forwarding over nesting.                                        |
| D10 | Type binding              | `*T?` is `*(T?)`; `(*T)?` is an optional pointer; references follow the same rule.                                                                                                                                               | It matches every other postfix suffix.                                                                           |
| D11 | Matching                  | Ordinary `match` covers presence patterns, sum members and the sides of a fallible; `catch` arms are exactly `match` arms over the error.                                                                                        | One compositional matching model works for nested values and for errors.                                        |
| D12 | Handlers                  | `x catch { arms }` hands its operand's error to arms that must cover it, `x !! v` replaces it, and `x !!;` drops it; passing an error on is `x!` or an explicit arm, `e => throw e`. There is no block form.                  | Every error is handled or passed on where the reader sees it; nothing is swallowed or rethrown implicitly.     |
| D13 | Error conversion          | Mapping an error is an arm: `value catch { e => throw Wrap(e, context) }` binds the complete error and may use local context; an error passes on unconverted only as itself, a member of a sum, or part of a larger sum.         | Adding a filename or other context needs no one-argument helper and no implicit conversion.                      |
| D14 | Inspection                | `is` tests sum membership, one optional level, a fallible's side, or any `match` pattern, whose names bind only where the test holds: the guarded body and the right of `&&`; interface tests stay unimplemented; no narrowing. | Extraction takes a pattern, the subject keeps its type, and membership never implies an interface.               |
| D15 | Used fallibles            | A fallible written as a statement on its own is an error; ignoring an error is written `x !!;`. Each postfix form needs a fallible operand.                                                                                       | An error can neither be dropped by accident nor leave through a call the reader cannot see.                      |
| D16 | Representation            | A fallible is a tagged aggregate whose success and error sides stay distinct; a shared layout may use only payload-preserving niches and never rewrites an inner tag.                                                           | Borrowed payload access and pass-through need every nested payload addressable in place.                         |
| D17 | Tooling                   | Every syntax form is supported by the formatter, dumps, and lint traversal.                                                                                                                                                      | Every fixture survives the workspace tooling.                                                                    |
| D18 | Migration                 | Conflicting identifiers were renamed before `none`, `fail`, `catch`, `throw` and `try` were reserved; `throws`, the four `try` forms and Core's `Result` coexisted with the postfix forms until the packages migrated, and were then removed, `try` and `throws` staying reserved so the parser names the replacement. | Coexistence alone could not prevent keyword breakage, and removal had to wait for an audited migration.          |
| D19 | Public errors             | Exact sum widening is available; named error variants keep a public abstraction and original causes.                                                                                                                             | An alias of a sum hides no dependency type and does not stabilize exhaustive callers.                            |
| D20 | Presence patterns         | `p?`, `p??`, and `none?` are the only spellings, the pattern mirroring the type `T?`; `.Some(p)` is rejected with the presence pattern as its help.                                                                                   | The case form is the one pattern grammar every level shares; `?` is left to optionals in expressions.            |
| D21 | Extension of native forms | Native forms are not `extend` targets and implement no interface; reusable operations are generic functions whose parameters spell the forms, and inference descends through them.                                               | Anonymous compiler-owned types have no declaring package to own a method set.                                    |
| D22 | Optional widening         | `A?` widens to `(A \| B)?` by injection or subset widening of the payload while preserving absence; presence is never constructed inside an existing optional.                                                                   | It mirrors the widening of an error into a larger sum, and identity still wins at the outer level.               |
| D23 | Collapse-safe `_`         | A `_` default arm is never diagnosed as unreachable; only typed, qualified, native, literal, and unit arms covered by earlier unguarded arms are.                                                                                | `x: T => ..., _ => ...` must stay valid when `T = U`.                                                            |
| D24 | Free-name binding         | An identifier pattern naming a type, alias, generic parameter, enum, variant, interface, constant, function, or module, or a case of the subject, is rejected instead of binding; shadowing a variable or parameter stays legal. | With typed patterns, `Options =>` is the obvious slip, and a bare binding silently matches everything.           |
| D25 | `Main`                    | `Main` has one signature, `func Main() -> int`, and cannot fail: steps that can fail are a function whose error `Main` handles, as in `return Run() !! 1;`.                                                                     | The exit status is an integer the program chooses; a failing `Main` would leave the status to a hidden wrapper.   |
| D26 | Postfix placement         | `x!` is a tight postfix operator; `!!` and `catch` bind as loosely as `??`, handle everything to their left, and do not mix with `??` unparenthesized. A form handles only its own operand.                                     | The exit sits at the call that causes it, and a handler's reach is the operand the reader sees.                  |
| D27 | Failing constructors      | A constructor may declare `-> Self ! E`; its call is a fallible like any other.                                                                                                                                                  | Construction that can fail keeps the constructor's name, and a value exists only once the constructor returns.   |
| D28 | No `finally`              | `finally` is reserved and rejected with a help pointing at `defer`.                                                                                                                                                              | `defer` and destructors already run on every exit, an error leaving included; a second cleanup form would compete with them. |
| D29 | Matching by side          | A typed pattern selects the side of a fallible its type is on, or members of an error sum; a type on both sides is rejected, and `.Success(p)` and `.Failure(p)` name the sides for generic code.                              | By-type inspection works as for any sum, and the overlap a generic instantiation can create costs only that.     |
| D30 | `if let` and `is`         | `if let pattern = x` and `while let` bind; `is` tests and never binds; an optional is tested with `== none` and `!= none`, which compare no payload. A binding comes first in a condition and joins others with `&&`. | A test compares and a binding declares, so a name never appears where nothing matched and no type changes after a test. |

After the migration, absence is only `T?` and failure only `T ! E`. A variant with `Success`/`Error` or `Some`/`None` cases is an ordinary variant whatever it is called: `?` and `??` reject it, a `Next` returning a `Some`/`None` variant is rejected at its declaration, and the case names are consulted only to word those diagnostics.

## Errors

A function that can fail returns a tagged aggregate holding its success or its error, and taking it apart is a test of the tag and a branch: to the continuation on success, and on failure to the handler's arms within the same function, or out of the function as an ordinary return of the aggregate. This is the value model, and it is chosen over table-driven unwinding for the reasons below. Revisit them before introducing anything that unwinds.

| #   | Topic                    | Decision                                                                                                                        | Reason                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1  | No unwinder              | The compiler emits no unwind tables, no call-frame information and no landing pads, and links no unwinder or personality routine. | The compiler writes its own objects and its own PE, ELF and Mach-O images for Windows, Linux, macOS and FreeBSD on two architectures. Unwinding would need a table format and an unwinder for each of the four systems, all of which a self-contained compiler would have to generate, link and keep correct itself. |
| E2  | Cost of an error         | An error costs what a return costs: a tag test and a branch at each frame it passes.                                            | Table-driven unwinding keeps the success path free but makes a throw 100 to 1000 times as expensive as a return, because the unwinder searches tables and walks frames. Rux errors are ordinary outcomes — a missing file, a malformed number — that a parser or an I/O loop meets often, not rare events.         |
| E3  | Code size                | Code grows only where errors are produced or handled.                                                                           | Unwind tables and landing pads typically add 10 to 20% to the size of a whole program, functions that never throw included.                                                                                                                                                                                       |
| E4  | Exits stay explicit      | Only `x!` and `throw` leave with an error, each an ordinary branch in the function's control flow.                              | Under unwinding every call becomes a possible exit, so ownership, drop flags, borrows and the optimizer would have to assume that any call may leave. Written exits leave the existing cleanup lowering and every later stage unchanged: HIR, LIR and the back ends see returns and branches.                       |
| E5  | No allocation            | An error travels in the caller's result slot, never on the heap.                                                                | An exception object usually lives on the heap, so reporting that memory ran out would itself need memory. A value-model error needs none.                                                                                                                                                                       |
| E6  | Typed errors             | The error type is part of the signature, `-> T ! E`, and an error passes on only as itself or within a larger sum.              | As in Swift's typed throws, Zig's error unions and Herb Sutter's static exceptions, a caller knows exactly what it must handle, and the error is a value of that type rather than a dynamic object matched by type at run time.                                                                                    |
| E7  | Free when nothing fails  | A function that cannot fail returns its plain type, and a call to it has no tag test.                                          | Code that cannot fail pays nothing for the existence of errors elsewhere.                                                                                                                                                                                                                                       |
| E8  | Panics do not unwind     | `Panic`, a failed check and process termination stop the program without running defers or destructors.                         | A panic reports a broken invariant; resuming or cleaning up after one would need the unwinder E1 rules out.                                                                                                                                                                                                       |

## Conversion Routes

Where a typed value meets a known native destination, aliases are resolved and sums normalized, exact identity wins, and otherwise the permitted routes are enumerated by the tag selections they produce. Exactly one route must apply; none is an incompatible type and several are an ambiguous construction that must be written out. Context flows into conditional and match arms but never invents a destination sum or chooses an error type.

| Destination   | Permitted implicit route                                                                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sum `A \| B`  | Inject an exact member or widen a subset sum; no conversion is searched inside members. An unsuffixed numeric literal targets the one member of its kind, independent of its value. |
| Optional `P?` | Construct outer presence when the source converts uniquely to `P`, or widen the payload while preserving absence.                                                                   |
| Fallible `T ! E` | Construct the success when the source converts to `T`, or widen the error sum of another fallible with the same success.                                                       |
| Anything else | Ordinary conversions only.                                                                                                                                                          |

Errors follow two rules of their own. A `throw` converts its operand to the function's error type, as a `return` value converts to the return type, so a member of a sum is injected. An error that `x!` passes on is never converted: it reaches the function's error side only by identity, as a member of a sum, or as a subset of a larger sum.

`throw`, `return`, `break`, `continue`, `Panic`, and no-return calls are diverging forms that never decide a match, `??` or `!!` result type, and they are accepted only as a statement, a whole arm body, or the whole right operand of `??` or `!!`.

## Representation and Ownership

- Every native level is a tagged aggregate with an 8-byte tag at offset 0 and each case's payload at `AlignUp(8, payloadAlign)`. Absent is tag 0 and present tag 1; in a fallible success is 0 and failure 1; a sum member's tag is its canonical index. Tags are not a stable public ABI.
- A zero-sized payload reserves no bytes anywhere: `sizeof(())` is 0 with alignment 1, `()?` is the tag alone, and `!E` is a tag plus `E`. Semantic layout, code-generation layout, both frame planners, and both call emitters read the same record.
- A borrowed subject is matched in place: bindings alias the payloads where they lie, and a subset binding reads the original tag through the recorded mapping. Such a view can be read and matched but not re-borrowed, passed by reference, stored, or moved; only a single-member binding writes through. An owned subset binding remaps tags, copying or moving with its subject.
- `?`, `??` and the error forms consume their evaluated operand. A named copyable operand is copied and a named move-only one is given away; a borrowed optional is never an operand. A throw site moves its success onward and its error to the handler or the caller with their move operations, so a payload whose move is prohibited is rejected at the site, or at instantiation for a type parameter. Propagation and `throw` capture the outgoing payload before running defers. A success or an error a form drops is destroyed where it is dropped.
- The state of each local at a handled operand is the state the handler's arms start from. An arm that leaves never returns to the continuing path, so a local moved only inside such an arm is still owned there.
- Equality compares tags level by level, then the active payload. A comparison supplies an expected type only to an operand without one of its own (`none`, a native constructor, an unsuffixed literal), so `opt == 5i32` and `sum == member` are rejected.

## Handling and Its Limits

A fallible that nothing uses would drop its error unseen, so one written as a statement on its own is `'Read' can fail with 'IoError', and the result is not used`. Ignoring an error is therefore always written: `F() !! none` turns it into `none`, and `F() !!;` drops it with the success. A fallible kept in a local or a field and destroyed later still drops its error without a mark; the check is made at the call.

## Public Error Boundaries

Signatures name their errors explicitly. Widening an internal error sum is convenient, but adding a member changes the public contract and can break exhaustive callers, and an alias hides none of its members. Prefer a named public error variant where callers should depend on a stable domain boundary, and wrap lower-level errors explicitly with their causes and context. There is no base error interface, automatic erasure, implicit conversion, or inferred error set.

## Non-Goals and Their Equivalents

Deliberately not introduced: optional chaining `?.`, inferred error sets, `From`-style implicit error conversion, a block form of handling, `guard let` (`if let` with an early exit takes its place: `let value = entry ?? return none;`), flow narrowing, closures, unwinding exceptions, `finally`, fallible loops, and `extend` or interface implementations on native forms.

| Wanted                              | Write                                                                                  |
| ----------------------------------- | -------------------------------------------------------------------------------------- |
| `let else`                          | `let v = option ?? return none;` or `let v = F() !! return ...;`                        |
| A fallback value                    | `F() !! fallback`                                                                      |
| `From` conversion                   | `F() catch { e => throw Wrap(e, context) }`                                            |
| `unwrap`/`expect` in a test         | `let value = F() !! Panic(message);`                                                   |
| Ignoring an error                   | `F() !! none`, or `F() !!;` as a statement                                             |
| Storing an outcome                  | `let kept = F();`, a `T ! E`                                                           |
| A `try { } catch { }` block         | A function of its own, handled where it is called: `Steps() catch { arms }`            |
| `finally`                           | `defer`                                                                                |
| A method on an optional             | A generic free function, `if let`, or a test, as in `entry != none`                    |
| Absence turned into an error        | `option ?? throw NotFound {}`                                                          |

## Where the Compiler Implements Them

- **Type model** (`Compiler/Types/Type.h`, `Type.cpp`): kinds `Sum`, `Optional`, and `Fallible`; `MakeSum` flattens, sorts by canonical spelling, deduplicates, and reduces singletons, and `Renormalize` repeats that after substitution; `MakeUnit` is the empty tuple; `MakeNoneValue` is the placeholder type of a contextual `none`. `MangledSpelling` escapes `?`, `|`, and `!` as `_O`, `_S`, and `_F` in linker names.
- **Conversions** (`Compiler/Types/NativeConversion.{h,cpp}`): `ClassifyNativeConversion(source, destination)` returns identity, a route of steps, incompatible, or ambiguous; `TypeRef::IsAssignableTo` defers to it whenever a native type is involved.
- **Layout** (`Compiler/Types/NativeLayout.{h,cpp}`): `ComputeNativeLayout` is the one layout record; semantic `LayoutOfTypeRef` and code generation's `RuntimeNativeLayout`, `RuntimeSizeOf`, `SizeOf`, and `AlignOf` all use it.
- **Pattern selection** (`Compiler/Types/NativeSelection.h`): `ClassifyNativeSelection(subject, annotation)` decides whether a typed pattern binds the whole subject, sum members, one presence level, or one side of a fallible.
- **Syntax** (`Syntax/Ast/Ast.h`, `Parser/ParserType.cpp`, `ParserExpr.cpp`, `ParserStmt.cpp`): `SumTypeExpr`, `OptionalTypeExpr`, and `FallibleTypeExpr`; `ErrorFormExpr` for `x!`, `x catch { arms }`, `x !! v` and `x !!;`; `TryExpr` for the optional `?`, `NativeConstructExpr`, `NoneExpr`, `DivergeExpr`; `FailStmt`, which `throw` builds; `TypedPattern` and `NonePattern`. The parser reports each removed spelling — `throws`, `try`, `fail`, `? else`, `finally` — with its replacement and reads it the new way so the rest of the file still parses.
- **Semantic analysis**: `TypeResolution.cpp` resolves the forms; `Assignments.cpp` routes conversions and records `nativeConversions`; `Throws.cpp` owns `throw`, the postfix error forms, the routing of each throw site to its handler or out of the function (`ResolvedThrowSite`, `ResolvedThrowHandler`), and handler coverage; `Statements.cpp` checks `return`, unit completion and an unused fallible; `Propagation.cpp` and `Iteration.cpp` check `?`, `??`, and `Next`, and reject a `?` on a fallible; `PatternCoverage.cpp` checks native coverage, rechecked per instantiation by `ValidateDeferredPatternChecks`.
- **Lowering**: `AstToHirNative.cpp` builds every level as a variant-form `HirEnumConstructExpr` with the native tag, every native pattern as a `HirEnumPattern` with that tag, widening as a match that rebuilds each alternative, and `?` and `??` as matches whose exits are ordinary returns. `AstToHirThrows.cpp` lowers `x!` the same way and a handler as a match on its operand's outcome whose failure arms are the handler's own, so defers and destructors run as for any return. HirToLir treats natives as aggregate enums with an `int64` tag, and both back ends pass them as aggregates.

## Migrating to the Error Forms

Each removed form is rejected with a `help:` line naming its replacement.

| Old usage                                                                 | Target form                                                                                     |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `-> T throws E`, `throws E` after the parameters                          | `-> T ! E`, `-> !E`                                                                             |
| `try F()`                                                                 | `F()!`, after each call that can fail: `let x = A()!.B()!;`                                    |
| `try F() catch { arms }`                                                  | `F() catch { arms }`                                                                            |
| `try? F()`                                                                | `F() !! none`                                                                                   |
| `try { ... } catch { arms }`                                              | A function holding the statements, handled where it is called; one call is `F() catch { arms }` |
| `try F() catch { _ => {} };`                                              | `F() !!;`                                                                                       |
| `Result<T, E>`, built with `try .Success(F()) catch { e => .Failure(e) }` | The fallible itself: `let kept = F();`, a `T ! E`                                               |
| `fail error;`, `return .Failure(error);`                                  | `throw error;`                                                                                  |
| `return .Success(value);`                                                 | `return value;`                                                                                 |
| `value? else (e => mapped)`                                               | `value catch { e => throw mapped }`                                                             |
| `func Main() -> int ! E`, `func Main() -> !E`, `func Main() {}`           | `func Main() -> int` handling the error of a function that can fail: `return Run() !! 1;`       |
| `Option<T>`, `Option<Option<T>>`                                          | `T?`, `T??`                                                                                     |
| `Option::Some(value)`, `Option::None`                                     | The plain value, `none`                                                                         |
| Presence patterns `x?`, `x??`, `none?`                                    | Kept: `x?`, `x??`, `none?`                                                                       |
| `IsSome`/`IsNone`                                                         | `value is T`, or a presence match                                                               |
| `ValueOr` on an option / on a result                                      | `option ?? fallback` / `F() !! fallback`                                                        |
| Status enum with a success member (`-> IoError` with `None = 0`)          | `-> !E` with the success member, `IsOk`, and `IsError` removed                                  |
| Output slot beside a status (`Write(bytes, taken: *var uint) -> IoError`) | The slot becomes the result: `-> uint ! IoError`                                                |
| Output slot beside an option (`Replace(..., error: *var E) -> Option<V>`) | `-> V? ! E`                                                                                     |
| Iterator `Next -> Option<Item>`                                           | `Next -> Item?`                                                                                 |
| An interface requirement returning a status                               | Change the requirement and every implementation together; an implementation must match exactly |

Idioms that worked well during the first-party migration:

- A test whose steps can fail puts them in a function, `Run() -> !E`, that `Main` handles with `Run() !! return 1;`; an error exits with status 1 and fails the test.
- `F() !! Panic(message)` for an expected success inside a function that cannot fail, and, for an expected failure, a `match` on the outcome:

  ```rux
  match Parse(text) {
      .Success(_) => return 1,
      .Failure(error) => Assert(error == .Empty, "the empty text is refused"),
  }
  ```

- A `try` block whose arms all leave becomes a plain block whose calls each carry the arms; a block with one call becomes a `match` on that call's outcome, the rest of the block on the success side.
- An assertion that a failed constructor "comes back empty" is dropped: no value comes back.

Pitfalls:

- `!!` and `catch` take everything to their left, `+` included: write `base + (F() !! 0)`.
- `==` binds tighter than `??`: write `a == (b ?? c)`.
- `opt == none` and `opt != none` compare no payload; `opt == v` needs `==` on the payload, and makes `v` present to compare.
- A named move-only value as a `match` subject is written `move name`.
- A block arm `{ ... }` yields its last expression written without a ';', and `()` otherwise, so a `catch` arm recovers a non-unit success only with such a value or by leaving.
- An arm is outside its handler: an `x!` in it leaves the function, and its error goes to the caller.
- `x !! none` keeps an optional success at its level: on an `int? ! E` it is an `int?`, where `try?` gave an `int??`.

## Regression Coverage

The executable fixtures `Tests/Language/SumType`, `Optional`, `None`, `OptionalIteration`, `GenericSum`, `Coalescing`, `IsBinding`, and `FallibleMatch` exercise sums, optionals and the stored outcome, and `Throw`, `ErrorForms`, `ErrorPropagation`, `CatchArms`, `ErrorToNone`, `ErrorCleanup`, `MainExitStatus`, `FallibleInterface`, and `ThrowingConstructor` exercise errors end to end. The `NativeOutcomeSpellings`, `RemovedErrorSyntax`, `RemovedForms`, `RemovedLegacySyntax`, `TryRemoved`, `PostfixErrorForms`, `ErrorHandlerMixing`, `FallibleAsSuccess`, `FallibleTypedPatterns` and `Throws*` goldens pin the rejected spellings and the error diagnostics, and the `Native*` and `Throws*` unit tests cover each compiler stage. Changing any decision above means updating the affected fixtures and goldens in the same change.
