# Native Sums, Optionals, and Errors

This page records why the native outcome forms are shaped the way they are, why errors are thrown as values rather than unwound, where the compiler implements both, and how code written against the retired forms migrates. The user-facing rules themselves are in the language guide, under [Native Sums and Optionals](Language.md#native-sums-and-optionals) and [Errors: `throws`, `throw` and `try`](Language.md#errors-throws-throw-and-try); this page is the rationale and the map behind them. Revisit a decision here before changing the behavior that depends on it.

## Forms and Terms

| Form                    | Purpose                                                                                                   | Inspection                                                         |
| ----------------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `variant Event { ... }` | Alternatives distinguished by meaningful case names, even with identical payload types.                   | Named case patterns.                                               |
| `A \| B`                | One value of a set of distinct resolved types: a _sum_.                                                   | Typed patterns, qualified case patterns, `is`.                     |
| `T?`                    | A present `T` or absence: an _optional_, preserving every level.                                          | `.Some(p)`, `none`, typed presence patterns, `is`, `?`, `??`.      |
| `-> T throws E`         | A function that returns a `T` or throws an `E`. `throws E` after the parameters alone returns nothing.     | `try`, `try?`, `try ... catch { arms }`, `try { ... } catch { arms }`. |
| `Result<T, E>`          | Core's ordinary variant `Success(T)` / `Failure(E)`, for an outcome that must be kept as a value.          | Its case patterns and `is`, like any variant.                      |
| `()`                    | The built-in empty tuple, the _unit_, whose only value is also `()`.                                      | The pattern `()` or a binding.                                     |
| `union Storage { ... }` | Untagged overlapping storage.                                                                             | Field access.                                                      |

Diagnostics, lint messages, and these docs use one vocabulary: a _member_ is one type of a sum; a _level_ is one optional nesting step; the _native constructor_ is `.Some`, with `none` for absence; the _typed presence pattern_ is `v: T` on an optional subject. On the error side, a function's _error channel_ is the type its `throws` clause names; a _throw site_ is a call, operator or constructor whose callee throws, or a `throw`; a _handler_ is a `try` block, a `try ... catch` expression or a `try?`, which receives the errors its throw sites raise; and a throw site is _marked_ when a `try` covers it.

## Design Decisions

| #   | Topic                     | Decision                                                                                                                                                                                                                         | Reason                                                                                                           |
| --- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| D1  | Terminology               | `A \| B` is a _sum type_; `union` keeps naming overlapping storage.                                                                                                                                                              | Distinct storage contracts stay distinct in docs and diagnostics.                                                |
| D2  | Optional model            | `T?` is compiler-owned and non-collapsing; `T??` is distinct. There is no `None` type.                                                                                                                                           | Iterators and maps must tell a missing element from a present absent value.                                      |
| D3  | Optional construction     | `none` is outer absence; `.Some(value)` explicitly selects presence.                                                                                                                                                             | Every nested state is constructible without temporaries.                                                         |
| D4  | Generic sums              | `T \| U`, `E \| Timeout`, and repeated outer constructors are legal; sums normalize after substitution and dependent operations are rechecked.                                                                                   | Sum identity is a set of types, not left/right provenance; instantiation-time diagnostics are the accepted cost. |
| D5  | Member order              | Canonical order derives from the stable fully qualified resolved identity.                                                                                                                                                       | Independently compiled objects agree on the same concrete type.                                                  |
| D6  | Unit success              | The unit is the empty tuple `()`; a function declaring `throws E` and no return type completes with it.                                                                                                                         | One error model, with no library type recognized by name.                                                        |
| D7  | Errors are not values     | No fallible type can be written: `T ! E` is rejected with a help naming `-> T throws E`. An error is thrown, and an outcome that must be stored is Core's ordinary `Result<T, E>`, built with `try .Success(F()) catch { e => .Failure(e) }`. | An error is handled where it is raised or passed on visibly; keeping one is a deliberate choice that names a type. |
| D8  | Nesting                   | Nested optionals and optional error payloads are preserved; an optional error is grouped, `throws (E?)`.                                                                                                                        | Composition never erases a level or turns an inner absence into an outer one.                                    |
| D9  | Conversion                | Identity first; otherwise exactly one permitted construction or widening route, and competing interpretations are rejected.                                                                                                      | Expected-type convenience never silently chooses forwarding over nesting.                                        |
| D10 | Type binding              | `*T?` is `*(T?)`; `(*T)?` is an optional pointer; references follow the same rule.                                                                                                                                               | It matches every other postfix suffix.                                                                           |
| D11 | Matching                  | Ordinary `match` covers presence patterns and sum members; `catch` arms are exactly `match` arms over the error.                                                                                                                 | One compositional matching model works for nested values and for errors.                                        |
| D12 | Handlers                  | `try expr catch { arms }` and `try { ... } catch { arms }` hand what their throw sites raise to arms that must cover every error; passing an error on is an explicit arm, `e => throw e`.                                     | Every error is handled or passed on where the reader sees it; nothing is swallowed or rethrown implicitly.     |
| D13 | Error conversion          | Mapping an error is an arm: `try value catch { e => throw Wrap(e, context) }` binds the complete error and may use local context; an error passes on unconverted only as itself, a member of a sum, or part of a larger sum.   | Adding a filename or other context needs no one-argument helper and no implicit conversion.                      |
| D14 | Inspection                | `is` tests sum membership, one optional level, or any `match` pattern, whose names bind only where the test holds: the guarded body and the right of `&&`; interface tests stay unimplemented; no narrowing.                     | Extraction takes a pattern, the subject keeps its type, and membership never implies an interface.               |
| D15 | Marked throw sites        | Every throw site is covered by `try`, `try?`, `try ... catch` or a `try` block; an unmarked one is an error, and a `try` that covers none is a warning.                                                                         | An error can neither be dropped by accident nor leave through a call the reader cannot see.                      |
| D16 | Representation            | A throwing function returns a tagged aggregate whose success and error channels stay distinct; a shared layout may use only payload-preserving niches and never rewrites an inner tag.                                         | Borrowed payload access and pass-through need every nested payload addressable in place.                         |
| D17 | Tooling                   | Every syntax form is supported by the formatter, dumps, and lint traversal.                                                                                                                                                      | Every fixture survives the workspace tooling.                                                                    |
| D18 | Migration                 | Conflicting identifiers were renamed before `none`, `fail`, `catch`, `throw` and `try` were reserved; the shape-recognized `Result`/`Option` protocols, and then the `T ! E` spelling with its `?`, `? else`, postfix `catch` and `fail`, coexisted with their replacements until the packages migrated, and were then removed. | Coexistence alone could not prevent keyword breakage, and removal had to wait for an audited migration.          |
| D19 | Public errors             | Exact sum widening is available; named error variants keep a public abstraction and original causes.                                                                                                                             | An alias of a sum hides no dependency type and does not stabilize exhaustive callers.                            |
| D20 | Presence patterns         | `.Some(p)`, `.Some(.Some(p))`, and `.Some(none)` are the only spellings; the presence suffix `p?` is rejected with the case form as its help.                                                                                   | The case form is the one pattern grammar every level shares; `?` is left to optionals in expressions.            |
| D21 | Extension of native forms | Native forms are not `extend` targets and implement no interface; reusable operations are generic functions whose parameters spell the forms, and inference descends through them.                                               | Anonymous compiler-owned types have no declaring package to own a method set.                                    |
| D22 | Optional widening         | `A?` widens to `(A \| B)?` by injection or subset widening of the payload while preserving absence; presence is never constructed inside an existing optional.                                                                   | It mirrors the widening of an error into a larger sum, and identity still wins at the outer level.               |
| D23 | Collapse-safe `_`         | A `_` default arm is never diagnosed as unreachable; only typed, qualified, native, literal, and unit arms covered by earlier unguarded arms are.                                                                                | `x: T => ..., _ => ...` must stay valid when `T = U`.                                                            |
| D24 | Free-name binding         | An identifier pattern naming a type, alias, generic parameter, enum, variant, interface, constant, function, or module, or a case of the subject, is rejected instead of binding; shadowing a variable or parameter stays legal. | With typed patterns, `Options =>` is the obvious slip, and a bare binding silently matches everything.           |
| D25 | Throwing `Main`           | `Main` may declare `throws E`, with or without an `int` result; an error that reaches it runs ordinary cleanup and exits with status 1 without printing.                                                                         | Every executable test is an integer `Main`; otherwise each top-level `try` needs a wrapper.                      |
| D26 | `try` placement           | One `try` covers the whole expression to its right and is written where an expression starts; a `try` to the right of an operator is an error.                                                                                  | A mark reads as a statement-level marker, and one buried in an operand would hide which calls it covers.         |
| D27 | Throwing constructors     | A constructor may declare `-> Self throws E`; its call is a throw site.                                                                                                                                                          | Construction that can fail keeps the type's name instead of a `New` or `Create` factory, and a value exists only once the constructor returns. |
| D28 | No `finally`              | `finally` is reserved and rejected with a help pointing at `defer` inside the `try` block.                                                                                                                                       | `defer` and destructors already run on every exit, an error leaving included; a second cleanup form would compete with them. |

After the migration, absence is only `T?` and failure only `throws E`. A variant with `Success`/`Error` or `Some`/`None` cases is an ordinary variant whatever it is called, Core's `Result` included: `?` and `??` reject it, a `Next` returning a `Some`/`None` variant is rejected at its declaration, and the case names are consulted only to word those diagnostics.

## Errors

A throwing function returns a tagged aggregate holding its success or its error, and each throw site is the call, a test of the tag, and a branch: to the continuation on success, and on failure to the handler's arms within the same function, or out of the function as an ordinary return of the aggregate. This is the value model, and it is chosen over table-driven unwinding for the reasons below. Revisit them before introducing anything that unwinds.

| #   | Topic                    | Decision                                                                                                                        | Reason                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E1  | No unwinder              | The compiler emits no unwind tables, no call-frame information and no landing pads, and links no unwinder or personality routine. | The compiler writes its own objects and its own PE, ELF and Mach-O images for Windows, Linux, macOS and FreeBSD on two architectures. Unwinding would need a table format and an unwinder for each of the four systems, all of which a self-contained compiler would have to generate, link and keep correct itself. |
| E2  | Cost of a throw          | A throw costs what a return costs: a tag test and a branch at each frame it passes.                                             | Table-driven unwinding keeps the success path free but makes a throw 100 to 1000 times as expensive as a return, because the unwinder searches tables and walks frames. Rux errors are ordinary outcomes — a missing file, a malformed number — that a parser or an I/O loop meets often, not rare events.         |
| E3  | Code size                | Code grows only where errors are produced or handled.                                                                           | Unwind tables and landing pads typically add 10 to 20% to the size of a whole program, functions that never throw included.                                                                                                                                                                                       |
| E4  | Exits stay explicit      | Only a marked throw site is an exit edge, and it is an ordinary branch in the function's control flow.                          | Under unwinding every call becomes a possible exit, so ownership, drop flags, borrows and the optimizer would have to assume that any call may leave. Marked sites leave the existing cleanup lowering and every later stage unchanged: HIR, LIR and the back ends see returns and branches.                       |
| E5  | No allocation            | An error travels in the caller's result slot, never on the heap.                                                                | An exception object usually lives on the heap, so reporting that memory ran out would itself need memory. A value-model error needs none.                                                                                                                                                                       |
| E6  | Typed throws             | The error type is part of the signature, `-> T throws E`, and an error passes on only as itself or within a larger sum.         | As in Swift's typed throws, Zig's error unions and Herb Sutter's static exceptions, a caller knows exactly what it must handle, and the error is a value of that type rather than a dynamic object matched by type at run time.                                                                                    |
| E7  | Free when nothing throws | A function without `throws` returns its plain type, and a call to it has no tag test.                                           | Code that cannot fail pays nothing for the existence of errors elsewhere.                                                                                                                                                                                                                                       |
| E8  | Panics do not unwind     | `Panic`, a failed check and process termination stop the program without running defers or destructors.                         | A panic reports a broken invariant; resuming or cleaning up after one would need the unwinder E1 rules out.                                                                                                                                                                                                       |

## Conversion Routes

Where a typed value meets a known native destination, aliases are resolved and sums normalized, exact identity wins, and otherwise the permitted routes are enumerated by the tag selections they produce. Exactly one route must apply; none is an incompatible type and several are an ambiguous construction that must be written out. Context flows into conditional and match arms but never invents a destination sum or chooses an error type.

| Destination   | Permitted implicit route                                                                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sum `A \| B`  | Inject an exact member or widen a subset sum; no conversion is searched inside members. An unsuffixed numeric literal targets the one member of its kind, independent of its value. |
| Optional `P?` | Construct outer presence when the source converts uniquely to `P`, or widen the payload while preserving absence.                                                                   |
| Anything else | Ordinary conversions only.                                                                                                                                                          |

Errors follow two rules of their own. A `throw` converts its operand to the error channel it goes to, as a `return` value converts to the return type, so a member of a sum channel is injected. An error raised by a throw site is never converted: it reaches the function's channel only by identity, as a member of a sum, or as a subset of a larger sum, and a handler takes the sum of the error types thrown to it.

`throw`, `return`, `break`, `continue`, `Panic`, and no-return calls are diverging forms that never decide a match or `??` result type, and they are accepted only as a statement, a whole arm body, or the whole right operand of `??`.

## Representation and Ownership

- Every native level is a tagged aggregate with an 8-byte tag at offset 0 and each case's payload at `AlignUp(8, payloadAlign)`. Absent is tag 0 and present tag 1; in a throwing function's result success is 0 and failure 1; a sum member's tag is its canonical index. Tags are not a stable public ABI.
- A zero-sized payload reserves no bytes anywhere: `sizeof(())` is 0 with alignment 1, `()?` is the tag alone, and a function that throws `E` and returns nothing returns a tag plus `E`. Semantic layout, code-generation layout, both frame planners, and both call emitters read the same record.
- A borrowed subject is matched in place: bindings alias the payloads where they lie, and a subset binding reads the original tag through the recorded mapping. Such a view can be read and matched but not re-borrowed, passed by reference, stored, or moved; only a single-member binding writes through. An owned subset binding remaps tags, copying or moving with its subject.
- `?` and `??` consume their evaluated operand. A named copyable operand is copied and a named move-only one is written `(move value)?`; a borrowed optional is never an operand. A throw site moves its success onward and its error to the handler or the caller with their move operations, so a payload whose move is prohibited is rejected at the site, or at instantiation for a type parameter. Propagation and `throw` capture the outgoing payload before running defers.
- The state of each local at a throw site is the state the handler's arms start from, so a value moved after one throwing call and before another is possibly moved in the arms. An arm that leaves never returns to the continuing path, so a local moved only inside such an arm is still owned there.
- Equality compares tags level by level, then the active payload. A comparison supplies an expected type only to an operand without one of its own (`none`, a native constructor, an unsuffixed literal), so `opt == 5i32` and `sum == member` are rejected.

## Marking and Its Limits

Marking replaces the discard checks the older fallible values needed. A throwing call returns no value that could be dropped: it is a throw site, and an unmarked one is `call to 'Read' can throw 'IoError' but is not marked with 'try'`. Ignoring an error is therefore always written: `try? F()` turns it into `none`, and `try Close(file) catch { _ => {} };` drops it for a call that returns nothing. A `try` that covers no throw site is the warning `'try' has no call that can throw`. An error that must outlive the call is stored as a `Result<T, E>`, which is an ordinary value with no discard check of its own.

## Public Error Boundaries

Signatures name their error channels explicitly. Widening an internal error sum is convenient, but adding a member changes the public contract and can break exhaustive callers, and an alias hides none of its members. Prefer a named public error variant where callers should depend on a stable domain boundary, and wrap lower-level errors explicitly with their causes and context. There is no base error interface, automatic erasure, implicit conversion, or inferred error set.

## Non-Goals and Their Equivalents

Deliberately not introduced: optional chaining `?.`, a brace-less `catch fallback`, inferred error sets, `From`-style implicit error conversion, `if let`/`guard let` (binding `is` takes their place: `if entry is .Some(value) { ... }`), flow narrowing, closures, unwinding exceptions, `finally`, fallible loops, and `extend` or interface implementations on native forms.

| Wanted                              | Write                                                                                  |
| ----------------------------------- | -------------------------------------------------------------------------------------- |
| `let else`                          | `let v = option ?? return none;` or `let v = try F() catch { _ => return ... };`        |
| A bare `catch fallback`             | `try F() catch { _ => fallback }`                                                      |
| `From` conversion                   | `try F() catch { e => throw Wrap(e, context) }`                                        |
| `unwrap`/`expect` in a test         | `let value = try F() catch { e => Panic(message) };`                                   |
| Ignoring an error                   | `try? F()`, or `try F() catch { _ => {} };` when `F` returns nothing                   |
| Storing an outcome                  | `let kept: Result<T, E> = try .Success(F()) catch { e => .Failure(e) };`               |
| `finally`                           | `defer` inside the `try` block                                                         |
| A method on an optional             | A generic free function, or binding `is`, as in `entry is .Some(_)`                    |
| Absence turned into an error        | `option ?? throw NotFound {}`                                                          |

## Where the Compiler Implements Them

- **Type model** (`Compiler/Types/Type.h`, `Type.cpp`): kinds `Sum`, `Optional`, and `Fallible`, the last of which now only describes what a throwing function returns; `MakeSum` flattens, sorts by canonical spelling, deduplicates, and reduces singletons, and `Renormalize` repeats that after substitution; `MakeUnit` is the empty tuple; `MakeNoneValue` is the placeholder type of a contextual `none`. `MangledSpelling` escapes `?`, `|`, and `!` as `_O`, `_S`, and `_F` in linker names.
- **Conversions** (`Compiler/Types/NativeConversion.{h,cpp}`): `ClassifyNativeConversion(source, destination)` returns identity, a route of steps, incompatible, or ambiguous; `TypeRef::IsAssignableTo` defers to it whenever a native type is involved.
- **Layout** (`Compiler/Types/NativeLayout.{h,cpp}`): `ComputeNativeLayout` is the one layout record; semantic `LayoutOfTypeRef` and code generation's `RuntimeNativeLayout`, `RuntimeSizeOf`, `SizeOf`, and `AlignOf` all use it.
- **Pattern selection** (`Compiler/Types/NativeSelection.h`): `ClassifyNativeSelection(subject, annotation)` decides whether a typed pattern binds the whole subject, sum members, or one presence level.
- **Syntax** (`Syntax/Ast/Ast.h`, `Parser/ParserType.cpp`, `ParserExpr.cpp`, `ParserStmt.cpp`): `SumTypeExpr`, `OptionalTypeExpr`, and `FallibleTypeExpr`, which a `throws` clause builds; `TryMarkExpr` for `try`, `try?` and `try ... catch`, `TryStmt` for a `try` block, `TryExpr` for the optional `?`, `NativeConstructExpr`, `NoneExpr`, `DivergeExpr`; `FailStmt`, which `throw` builds; `TypedPattern` and `NonePattern`. The parser reports each removed spelling — `T ! E`, `fail`, `? else`, a `catch` that does not follow `try`, `finally` — with its replacement and reads it the old way so the rest of the file still parses.
- **Semantic analysis**: `TypeResolution.cpp` resolves the forms; `Assignments.cpp` routes conversions and records `nativeConversions`; `Throws.cpp` owns `throws` clauses, `throw`, the four `try` forms, the routing of each throw site to its handler or channel (`ResolvedThrowSite`, `ResolvedThrowHandler`), and handler coverage; `Statements.cpp` checks `return` and unit completion; `Propagation.cpp` and `Iteration.cpp` check `?`, `??`, and `Next`, and reject a `?` on a throwing call; `PatternCoverage.cpp` checks native coverage, rechecked per instantiation by `ValidateDeferredPatternChecks`.
- **Lowering**: `AstToHirNative.cpp` builds every level as a variant-form `HirEnumConstructExpr` with the native tag, every native pattern as a `HirEnumPattern` with that tag, widening as a match that rebuilds each alternative, and `?` and `??` as matches whose exits are ordinary returns. `AstToHirThrows.cpp` builds a throw site the same way and sends a handled error into its handler's slot and out of the code the handler covers by a labeled `break`, so defers and destructors run on the way. HirToLir treats natives as aggregate enums with an `int64` tag, and both back ends pass them as aggregates.

## Migrating to Typed Throws

Each removed form is rejected with a `help:` line naming its replacement.

| Old usage                                                                 | Target form                                                                                     |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `-> T ! E`                                                                | `-> T throws E`                                                                                 |
| `-> ! E`                                                                  | `throws E` after the parameters                                                                 |
| A stored `T ! E` field, local or parameter                                | `Result<T, E>`, built with `try .Success(F()) catch { e => .Failure(e) }`                       |
| `fail error;`, `return .Failure(error);`                                  | `throw error;`                                                                                  |
| `return .Success(value);`                                                 | `return value;`                                                                                 |
| `value?` on a fallible                                                    | `try value`, written once before the whole expression: `let x = try A().B();`                   |
| `value? else (e => mapped)`                                               | `try value catch { e => throw mapped }`                                                         |
| `value catch { arms }`                                                    | `try value catch { arms }`; a rethrow is an explicit arm, `e => throw e`                        |
| A `match` on `.Success(p)` and `.Failure(p)` of a call                    | `try F() catch { arms }`, or a `try { ... } catch { arms }` block                               |
| `outcome is .Success(_)`                                                  | `(try? F()) is .Some(_)`, or ask a stored `Result`                                              |
| `catch { else => {} }`                                                    | `try F() catch { _ => {} }`                                                                     |
| `func Main() -> int ! E`                                                  | `func Main() -> int throws E`                                                                   |
| `Result<T, E>` (the retired shape-recognized variant)                     | `-> T throws E`; Core's `Result` is now an ordinary variant with no operator support            |
| `Option<T>`, `Option<Option<T>>`                                          | `T?`, `T??`                                                                                     |
| `Option::Some(value)`, `Option::None`                                     | `.Some(value)` (or a plain value when unambiguous), `none`                                      |
| Presence patterns `x?`, `x??`, `none?`                                    | `.Some(x)`, `.Some(.Some(x))`, `.Some(none)`                                                    |
| `IsSome`/`IsNone`                                                         | `value is T`, or a presence match                                                               |
| `ValueOr` on an option / on a result                                      | `option ?? fallback` / `try F() catch { _ => fallback }`                                        |
| Status enum with a success member (`-> IoError` with `None = 0`)          | `throws E` with the success member, `IsOk`, and `IsError` removed                               |
| Output slot beside a status (`Write(bytes, taken: *var uint) -> IoError`) | The slot becomes the result: `-> uint throws IoError`                                           |
| Output slot beside an option (`Replace(..., error: *var E) -> Option<V>`) | `-> V? throws E`                                                                                |
| Iterator `Next -> Option<Item>`                                           | `Next -> Item?`                                                                                 |
| An interface requirement returning a status                               | Change the requirement and every implementation together; an implementation must match exactly |

Idioms that worked well during the first-party migration:

- A test `Main` declared `-> int throws E` lets every step use `try`; an error exits with status 1 and fails the test.
- `try call() catch { _ => Panic(message) }` for an expected success inside a function that does not throw, and, for an expected failure, a helper that returns the error it caught:

  ```rux
  func Refusal(text: char8[..]) -> ParseError? {
      let _ = try Parse(text) catch { error => return error };
      return none;
  }
  ```

- Cleanup whose outcome does not matter writes `try Close(file) catch { _ => {} };`. Inside a `defer` or a destructor no error may leave, so a call there that throws is handled this way or with `try?`.
- An assertion that a failed constructor "comes back empty" is dropped: no value comes back.

Pitfalls:

- `try` covers everything to its right, `??` included: write `(try? F()) ?? fallback`.
- `==` binds tighter than `??`: write `a == (b ?? c)`.
- `opt == none` and `opt == .Some(v)` need `==` on the payload; where the payload has none, test `opt is T` or match.
- A named move-only value as a `match` subject is written `move name`.
- A block arm `{ ... }` yields its last expression written without a ';', and `()` otherwise, so a `catch` arm recovers a non-unit success only with such a value or by leaving.
- An arm is outside its handler: a call in it needs its own `try`, and its error goes to the next handler out.

## Regression Coverage

The executable fixtures `Tests/Language/SumType`, `Optional`, `None`, `OptionalIteration`, `GenericSum`, `Coalescing`, `IsBinding`, and `Result` exercise sums, optionals and the stored outcome, and `Throw`, `Try`, `TryPropagation`, `TryCatch`, `TryOptional`, `TryDefer`, `ThrowsMain`, `ThrowsInterface`, and `ThrowingConstructor` exercise typed throws end to end. The `NativeOutcomeSpellings`, `RemovedErrorSyntax`, `RemovedForms`, `RemovedLegacySyntax`, `Throws*` and `Try*` goldens pin the rejected spellings and the throw-site diagnostics, and the `Native*` and `Throws*` unit tests cover each compiler stage. Changing any decision above means updating the affected fixtures and goldens in the same change.
